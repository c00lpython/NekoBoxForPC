# Тестовая дисциплина — глобальное правило

## Первый заход в проект / новый крупный модуль
1. Скан кодовой базы по модулям/файлам — НЕ всё разом одним проходом.
   Один модуль → покрыть тестами → показать мне → пауза на подтверждение → 
   следующий модуль. Массовая генерация тестов без проверки создаёт 
   покрытие, которому нельзя доверять.
2. Для каждой функции/класса — отдельный unit-тест, а не один тест 
   на несколько сущностей сразу.
3. Приоритет по уровням пирамиды (строится последовательно, но это 
   рабочий порядок дисциплины, не жёсткая техническая зависимость 
   Security/Load от Functional):
   Unit → Integration → Functional → Security → Load

## Иерархия test-manager'ов
Каждый уровень имеет свой раннер, ответственный за (а) обнаружение 
непокрытых тестами функций/классов ("gap scan") и (б) единую команду 
запуска всего слоя. Это дополнение к pytest, не замена:
- unit_manager.py — сканирует src на функции/классы без unit-теста, 
  прогоняет tests/unit/
- integrational_manager.py — тесты взаимодействия уже покрытых 
  Unit-модулей между собой, прогоняет tests/integration/
- functional_manager.py, security_manager.py, load_manager.py — 
  по аналогии, создаются когда дойдёт очередь до соответствующего 
  уровня, не заранее

## Правило изменения тестов (НЕ "никогда не менять")
Менять существующий тест можно ТОЛЬКО если:
- добавляется фича, расширяющая покрытие
- осознанно меняется требуемое поведение функции — и тест обновляется 
  вместе с ней в том же изменении, отражая новое поведение
ЗАПРЕЩЕНО менять тест, чтобы он прошёл при сломанном коде — чинить 
нужно код, не тест.

## При изменении существующей фичи
1. Перед правкой — найти все тесты, покрывающие изменяемую функцию/класс 
   (по имени функции в tests/, не только в соседнем файле)
2. Оценить: меняется контракт (сигнатура, возвращаемое значение, побочные 
   эффекты) или только внутренняя реализация?
   - Только реализация → тесты остаются как есть, должны пройти без правок
   - Контракт меняется → тест обновляется в том же изменении, с явным 
     указанием мне, что и почему изменилось в ожидаемом поведении
3. После правки — прогнать minimum: тесты изменённого модуля + 
   integration-тесты, если модуль имеет внешние вызовы

## Перед любым коммитом/сдачей задачи
python -m pytest tests/ -v (весь набор, не только новые/изменённые файлы)
Хотя бы один красный тест — почини или явно сообщи, не отчитывайся 
об успехе.
